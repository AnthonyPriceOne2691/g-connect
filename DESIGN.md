# G connect — дизайн

**Что это.** Единый слой доступа агента к Google Drive / Docs / Sheets (и локальным папкам), одинаково работающий из Cursor, Claude Desktop, Claude Code, Codex и любого другого MCP-клиента. Заменяет три разошедшиеся копии `Gdocs-tabs editor` одним core с двумя фасадами.

Версия: v0.1 (2026-09-01). Статус: дизайн зафиксирован, код не начат.

---

## 1. Зафиксированные решения

| # | Решение | Обоснование |
|---|---|---|
| D-1 | **Node.js + TypeScript** (Node 24, `googleapis` ^144) | ~2800 строк рабочей логики Docs/Sheets уже написаны на Node; TS-SDK для MCP — самый зрелый. Python-проекты (`local-web-agent`) при необходимости говорят с core через MCP или CLI, а не через импорт. |
| D-2 | **Только OAuth** (user-креды, Web-client + redirect `http://localhost:3333`) | Уже есть работающий `token.json`; Service Account требует расшаривания каждого файла на служебный email, что ломает ad-hoc работу. В attended-режиме (D-5) интерактивный вход при смене scopes не проблема — человек всё равно в сессии. |
| D-3 | **MVP = примитивы Docs + Sheets + Drive, приоритет — Sheets** | Основной живой сценарий — регулярное заполнение таблиц (§5, §6, §14), поэтому Sheets делается первым и глубже, чем Docs. Docs-review (якорные комментарии, хайлайты, `applyDocReview`), пресеты-пайплайны и Forms/Gmail/Calendar/Slides — отложены, но архитектура под них оставляет места расширения (§12). |
| D-4 | **Свой MCP-сервер сейчас; официальный Google MCP — опция позже** | Официальные remote MCP-серверы Google пишущие, но: Developer Preview (нужна заявка), Claude Desktop только на Pro/Max/Team/Enterprise через custom connector, и **на Docs всего 2 инструмента** (read + update) — ни комментариев, ни хайлайтов, ни tabs. Свой сервер не зависит от тарифа и preview-доступа. |
| D-5 | **Только attended-режим. Никакого крона и unattended-записи** | «Что писать в отчёты и какие колонки менять» — совместное решение с человеком, а не то, что можно зафиксировать в рецепте. Следствия: `dryRun`-превью и диалог — несущая часть, а не удобство; `launchd`/routines сознательно отвергнуты (§11). |
| D-6 | **Паритет с горячими клавишами Sheets как критерий полноты** (§6) | Список действий, которые ты делаешь руками, — готовая спецификация. Всё из него агент либо умеет через операцию, либо это исчезает как класс при работе через API, либо требует отдельного механизма (`Ctrl+Z` → §10). Третьего не бывает. |

| D-7 | **Резолвер имён колонок и значений — детерминированный, в core; модель не угадывает** (§8) | Требование «если я ошибся — уточнить на основе тех, что есть» должно вести себя одинаково в Cursor, Claude Desktop и у любого провайдера, и одинаково от запуска к запуску. Если отдать сопоставление модели, поведение станет случайным. Core возвращает типизированный ответ `needs_clarification` с кандидатами — модель только задаёт вопрос человеку. |

| D-8 | **Чтение и анализ — полноправный контур, а не побочный эффект записи** (§9). Широкий доступ на чтение, узкий на запись | Задача не только в повторяющихся действиях: нужно уметь осмысленно сканировать документы, листы, файлы на Диске и расшаренное. Отсюда асимметрия прав: читать можно всё, до чего есть доступ у аккаунта (включая shared drives и «доступные мне»), писать — только в цели из allowlist. И отсюда же главный риск: сканирование чужого контента — основной вектор prompt injection (§11.6). |
| D-9 | **Умный скан = детерминированные факты + модель для смысла; результат скана — артефакт-индекс, а не контекст** | Корпус не влезает в контекст и не должен туда попадать. Core механически собирает факты (структура, типы, дубли, битые формулы, расхождения ключей, свежесть), пишет их в локальный индекс, а модель интерпретирует уже выжимку. Иначе скан 200 файлов стоит дорого, не воспроизводится и не проверяется. |

| D-10 | **Универсальное ядро без привязки к конкретным таблицам. Ноль конфигурации на входе** | Ядро обязано работать с любой таблицей и любым документом «из коробки»: структура выводится из живого файла (§8.1, §9.3), а не берётся из заранее описанной схемы. Реестр целей со схемой и алиасами — **опциональный оверлей** для часто используемых файлов, а не предусловие. Никакие имена листов, колонок и рецептов в коде не зашиты. |

| D-11 | **Мозг подключаемый; ядро от модели не зависит** (§12) | Один и тот же механизм работает в трёх режимах: **A** — агент в чате/IDE (Claude Code, Cursor, Claude Desktop; модель — у клиента), **B** — локальная модель (Ollama) через собственный агент-раннер, **C** — любой провайдер по API-ключу через тот же раннер. Меняется только адаптер мозга; core, правила и инструменты — общие. |
| D-12 | **Правила работы с документами — артефакт репозитория, а не промпт клиента** (§12.4) | Иначе три режима разъедутся: в чате одно поведение, у локальной модели другое, по API-ключу третье. Правила лежат в `policy/`, отдаются MCP-клиентам как ресурс и описания инструментов, читаются раннером как системный блок и проверяются тестами. Один текст — три потребителя. |

| D-13 | **UI — четвёртый фасад того же ядра, поэтапно; не MVP** (§13) | UI обязателен в режимах B и C (D-11): у локальной модели и у раннера по API-ключу другого интерфейса просто нет. В режиме A интерфейсом служит сам чат, и дублировать его формой не нужно. Поэтому UI строится ступенями и всегда как клиент локального HTTP-фасада — никакой логики в UI, иначе появится второе ядро с расходящимся поведением. |

| D-14 | **Панель на React + Vite + TS + Tailwind; порядок фаз не меняется — UI идёт фазой 4** | Стек тот же, что во `local-web-agent`: знакомые привычки и компоненты, дешёвый рост до SSE и богатого диффа. Цена принята сознательно: второе дерево зависимостей и сборка в проекте, где ядро — серверный TS. UI остаётся фазой 4, потому что польза появляется с фазы 2 в режиме A, а панель приходит на готовое ядро, а не становится ставкой на неотлаженное. |

Ссылки по D-4: [Configure the Google Workspace MCP servers](https://developers.google.com/workspace/guides/configure-mcp-servers), [Sheets MCP server](https://developers.google.com/workspace/sheets/api/guides/configure-mcp-server).

## 2. Архитектура

```
G connect/
  package.json
  src/
    core/
      auth.ts            # OAuth: профили, refresh, локальный redirect-сервер
      profiles.ts        # ~/.gconnect/<account>/{credentials,token}.json
      targets.ts         # реестр целей: alias -> {id, type, allow}
      retry.ts           # backoff на 429/5xx (порт из run.js)
      docs/              # примитивы Docs
      sheets/            # примитивы Sheets + карта заголовков, upsert по ключу
      drive/             # примитивы Drive
      selectors.ts       # текстовые селекторы -> startIndex/endIndex
      resolver.ts        # имена колонок и значения: 6 ступеней -> ok | preview | clarify (§8)
      profile.ts         # профиль колонок живой таблицы: типы, enum, формулы, protected
      scan/              # воронка: инвентарь -> карта -> выборка -> свод, checks, бюджет
      index/             # локальный индекс сканов + diff между запусками
      providers/         # google | local — единый интерфейс для Диска и папок на диске
      paragraphIndex.ts  # порт lib/docParagraphIndex.js
      audit.ts           # журнал записей + снапшот ревизии перед правкой
      ops.ts             # схема операций gc_apply (zod) + валидация
    mcp/
      server.ts          # stdio-транспорт, регистрация инструментов
      tools/*.ts         # gc_targets | gc_read | gc_scan | gc_apply | gc_undo | gc_search
    http/
      server.ts          # локальный фасад ядра на 127.0.0.1 для UI и раннера (§13.2)
    agent/
      runner.ts          # свой агентный цикл для режимов B и C (§12.2, §12.3)
      brains/            # адаптеры: ollama | anthropic | openai-compatible
    policy/
      rules.md           # правила работы с документами (для мозга)
      rules.json         # машинная часть правил (исполняется в core, §12.4)
    cli/
      main.ts            # actions.json / пресеты — для крона и батчей
  ui/                    # ступень 1: панель React+Vite+TS+Tailwind, клиент http/ (§13.3)
      recipes/dailyLog.ts # сбор черновика итога дня (§14) — запускается человеком
```

**Один core, два фасада.** MCP — интерфейс для агентов (провайдер-независимый). CLI — для крона, Telegram-ботов и детерминированных батчей, где LLM не нужен. Оба вызывают один и тот же `core`; логика не дублируется ни строчкой.

**Транспорт MCP:** stdio для MVP (локально, без сети). HTTP-транспорт — только если понадобится удалённый доступ; тогда обязательны auth и bind на `127.0.0.1`.

## 3. Контракт инструментов

Принципиально: **не выставлять 30 мелких инструментов**. Это раздувает контекст, а агент начинает ошибаться в арифметике `startIndex`. Шесть «толстых» инструментов на MVP:

### `gc_targets`
Список доступных целей из реестра: `alias`, `type` (doc/sheet/folder), `id`, права (`read` / `write`). Без параметров. Возвращает то, что агенту разрешено трогать — и ничего больше.

### `gc_read`
```
{ target: alias | url | id,
  mode: "map" | "values" | "formulas" | "paragraphs" | "headings" | "meta",
  range?: "Sheet1!A1:D50", sheet?: string, limit?: number }
```
- `map` → **карта документа/таблицы**: листы, `usedRange`, заголовки колонок, примеры строк (§7). Основной режим первого обращения — с него агент начинает всегда.
- Doc → массив параграфов: `{ index, style, text, startIndex, endIndex }` (порт `docParagraphIndex.js`). Агент получает индексы, но адресует правки **селекторами**, не индексами.
- Sheet → значения или формулы диапазона.
- `meta` → название, владелец, последняя ревизия, ссылка.

### `gc_apply`
```
{ target, ops: Op[], dryRun?: boolean = true, expectRevision?: string }
```
`dryRun: true` — **значение по умолчанию**: возвращает разобранный план (что именно изменится, какой текст будет затронут, сколько символов) и не пишет. Реальная запись — только явным `dryRun: false`.

`expectRevision` — оптимистичная блокировка: если ревизия Drive изменилась с момента `gc_read`, запись отклоняется. Защита от гонок с живым редактированием в браузере.

Типы `Op` (порт встроенных действий `run.js`):

*Docs:* `appendText`, `insertText`, `replaceAllText`, `setParagraphStyle`, `updateTextStyle`, `deleteContentRange`, `createParagraphBullets`, `deleteParagraphBullets`, `insertPageBreak`, `insertTable`, `insertInlineImage`

*Sheets:* `updateValues`, `setFormula`, `setFormulas`, `clearValues`, `formatCells`, `mergeCells`, `unmergeCells`, `updateBorders`, `findReplace`

*Drive:* `createDoc`, `createSheet`, `createFolder` — с `saveAs`, чтобы следующие операции того же вызова адресовали только что созданный файл (поведение уже есть в `run.js`).

### `gc_scan`
```
{ scope: { where: "myDrive" | "sharedWithMe" | "sharedDrives" | "folder" | "local",
           folderId?, path?, recursive?: boolean },
  filter?: { type?, nameContains?, fullText?, modifiedAfter?, owner? },
  depth: "inventory" | "map" | "sample",
  checks?: ["emptyRequired","duplicateKeys","brokenFormulas","typeDrift","staleRows","headerDrift"],
  budget?: { maxFiles?, maxRowsPerFile?, maxTokens? } }
```
Воронка сканирования корпуса (§9). Возвращает свод + путь к файлу-индексу; ничего не пишет в документы.

### `gc_undo`
```
{ target, opId?: string, last?: number = 1 }
```
Откат последних записей сессии обратной записью, со сверкой ревизии. Механизм и его границы — §10.

### `gc_search`
Поиск по Drive: имя, тип, папка, время изменения → список `{ id, name, type, url }`. Нужен, чтобы агент не требовал ссылок вручную.

## 4. Адресация: селекторы вместо индексов

Ключевое отличие от голого Docs API. Агент указывает **что** правит, core вычисляет **где**:

```json
{ "op": "updateTextStyle", "where": { "paragraph": { "textStartsWith": "Прогноз на матч" } }, "bold": true }
{ "op": "insertText", "where": { "afterHeading": "H2: Составы" }, "text": "..." }
{ "op": "replaceAllText", "find": "Fluminense", "replace": "Fluminense FC" }
```

Поддерживаемые селекторы: `paragraphIndex` (из `gc_read`), `textStartsWith`, `textContains`, `afterHeading`, `firstParagraph`, `lastParagraph`, явная пара `startIndex/endIndex` (escape hatch). Неоднозначный селектор (совпало >1 места) — **ошибка**, а не «возьму первое»: даёт агенту сигнал уточнить, вместо тихой порчи документа.

Индексы Docs API сдвигаются после каждой правки, поэтому core пересчитывает селекторы **между** операциями одного `gc_apply`, а не один раз на входе.

## 5. Заполнение таблиц: строки, колонки, идемпотентность

Основной сценарий проекта — не разовая правка, а **регулярное дописывание данных в таблицы по мере роста проектов и в конце каждого рабочего дня**. Голый A1-диапазон для этого не годится: колонки переставляют, строки вставляют, и `Sheet1!D17` через неделю указывает не туда. Поэтому в `gc_apply` для Sheets — адресация по **именам колонок и ключу строки**.

### Операции

```json
{ "op": "appendRow", "sheet": "Daily log",
  "values": { "Дата": "2026-09-01", "Проект": "G connect", "Статус": "дизайн", "Часы": 2 } }

{ "op": "upsertRow", "sheet": "Daily log",
  "key": { "Дата": "2026-09-01", "Проект": "G connect" },
  "values": { "Статус": "в работе", "Часы": 3, "Комментарий": "..." } }

{ "op": "setCells", "sheet": "Projects",
  "where": { "Проект": "G connect" },
  "values": { "Фаза": "1", "Обновлено": "2026-09-01" } }
```

- `headerRow` (по умолчанию 1) — строка заголовков; core сам сопоставляет имя колонки с буквой и кэширует карту на вызов.
- Неизвестное имя колонки не создаёт колонку молча и не падает ошибкой: включается резолвер (§8) — точное совпадение и нормализация проходят молча, близкий кандидат проговаривается в превью, неоднозначность превращается в вопрос. Создание колонки — только явным `addColumn`.
- `where` / `key`, совпавшие с несколькими строками, — ошибка (как и с селекторами Docs, §4).

### Идемпотентность

`upsertRow` с ключом (обычно `дата + проект`) — обязательный режим для ежедневных записей. Повторный запуск того же дня перезаписывает строку, а не плодит дубликаты: cron может сработать дважды, агент может переспросить, ноутбук может проснуться позже. `appendRow` — только там, где дубликат осмыслен (лог событий).

### Схема таблицы как опциональный контракт

По умолчанию схема **не нужна**: core выводит колонки, типы и допустимые значения из самой таблицы (§8.1). Оверлей ниже — для файлов, с которыми работаешь постоянно и хочешь жёстких гарантий. Пример формата (не привязка к конкретной таблице):

```json
{ "alias": "daily-log", "type": "sheet", "id": "...", "allow": "write",
  "sheet": "Daily log", "headerRow": 1,
  "columns": { "Дата": "date", "Проект": "string", "Статус": "enum:дизайн|в работе|готово", "Часы": "number" },
  "aliases": { "Часы": ["затрачено", "time"], "Проект": ["project", "проектик"] },
  "key": ["Дата", "Проект"] }
```

Если оверлей задан, он становится контрактом. Схема в реестре — то, что ты зафиксировал руками; профиль колонок (§8.1) — то, что core вычитал из живой таблицы. Расхождение между ними (колонку переименовали, в enum появилось новое значение) сообщается, а не игнорируется. Core валидирует значения до записи: тип, обязательность, допустимые значения enum. Это дешёвая защита от того, что агент напишет «сегодня» в колонку даты или «почти готово» в enum. Схема также идёт в описание `gc_targets`, поэтому агент видит формат заранее и не угадывает.

## 6. Паритет с горячими клавишами: что агент обязан уметь

Список быстрых команд, которыми ты работаешь руками, — это спецификация полноты. Каждая строка попадает в одну из трёх категорий, и категорию нельзя выбрать произвольно: она вытекает из того, что у API нет курсора, выделения и буфера обмена.

### 6.1 Прямой аналог — уже есть в `run.js`

| Горячая клавиша | Операция |
|---|---|
| `Ctrl+N` создать таблицу | `createSheet` / `createDoc` / `createFolder` |
| `Ctrl+O` открыть | резолв цели по alias, URL или ID (§3, `gc_targets`) |
| ввод значения в ячейку | `updateValues`, `setCells`, `appendRow`, `upsertRow` |
| `=` формула, `Shift+F11` вставить функцию | `setFormula`, `setFormulas` |
| `Ctrl+B`, `Ctrl+I` | `formatCells` (bold, italic, backgroundColor) |
| `Ctrl+F` поиск, замена | `findReplace` |
| `Ctrl+Z`… но только на уровне «не писать лишнего» | `dryRun` (§11.1) — полноценный undo см. §10 |

### 6.2 Пробелы — надо дописать в core (ничего сложного, но сейчас этого нет)

| Горячая клавиша | Нужная операция | Основа в Sheets API |
|---|---|---|
| `Ctrl+U` подчёркивание | `formatCells.underline` | `repeatCell` → `textFormat.underline` |
| `Ctrl+Shift+E / L / R` выравнивание | `formatCells.align` | `textFormat` → `horizontalAlignment` |
| `Ctrl+Shift+=` / `+` строка выше/ниже | `insertRows` (относительно строки по ключу) | `insertDimension` |
| `Alt+I,C,C` / `Alt+I,C,O` столбец слева/справа | `insertColumns` (относительно колонки по имени) | `insertDimension` |
| `Shift+F11` вставить лист | `addSheet` | `addSheet` |
| `Ctrl+C` / `Ctrl+V` / `Ctrl+X` | `copyRange`, `cutRange` | `copyPaste`, `cutPaste` |
| `Ctrl+Shift+V` вставить без форматирования | `copyRange` с `paste: "values"` | `pasteType: PASTE_VALUES` |
| автозаполнение (маркер) | `autoFill` | `autoFill` |
| удаление строк/столбцов (в списке нет, но парно нужно) | `deleteRows`, `deleteColumns` | `deleteDimension` |

Проверено по коду: `formatCells` в `run.js` умеет только `bold` / `italic` / `backgroundColor` — подчёркивания и выравнивания там нет; операций вставки строк, столбцов и листов, копирования и автозаполнения нет вообще.

### 6.3 Исчезают как класс — и это хорошая новость

Не «не поддерживаем», а «при работе через API этого вопроса не существует»:

- **`Ctrl+S` и ожидание автосохранения.** Записи через API применяются сразу и атомарно. Твоя частая проблема из списка — «внёс данные, не дождался 3–5 секунд, закрыл таблицу» — при таком доступе невозможна в принципе: либо операция вернула успех и данные в таблице, либо вернула ошибку и не записано ничего.
- **Навигация курсором:** `Enter`, `Shift+Enter`, `Tab`, `Shift+Tab`, стрелки, `Home`, `End`. У агента нет курсора — он адресует диапазон или строку по ключу напрямую, без «дойти до».
- **Выделение:** `Ctrl+A`, `Shift+Arrow`, `Shift+Space` (строка), `Ctrl+Space` (столбец). Выделения нет; «вся строка» и «весь столбец» выражаются адресацией по ключу строки и имени колонки (§5).
- **`Ctrl+Home` / `Ctrl+End` / `Ctrl+Arrow Up|Down`.** По сути это вопрос «где начинаются и где кончаются данные». Ответ даёт `usedRange` в карте таблицы (§7) — это не операция, а свойство, которое агент видит до любой записи.
- **`Alt+F` / `Alt+E` (меню Файл/Правка).** Оболочка UI, эквивалента не требует.

## 7. Видимость: как агент «видит» документы и таблицы

Требование «он должен их видеть» — отдельная подсистема, и её нельзя решить простым «прочитай лист целиком»: живая таблица на несколько тысяч строк выжигает контекст и деньги, а агент всё равно теряется. Поэтому видимость **двухступенчатая**.

**Ступень 1 — дешёвая карта** (`gc_read` с `mode: "map"`), десятки строк вывода вместо тысяч:

- список листов (tabs) с размером сетки и `usedRange` — где реально кончаются данные;
- строка заголовков каждого листа (имена колонок как они есть) + закреплённые строки;
- количество заполненных строк, именованные диапазоны, фильтры;
- 3–5 примеров строк, чтобы агент видел формат значений, а не угадывал его;
- для Doc — оглавление по заголовкам (H1–H6) и список tabs.

**Ступень 2 — точечное чтение** (`mode: "values" | "formulas" | "paragraphs"`) по конкретному диапазону, фильтру или ключу, с обязательным `limit`. Если вывод усечён, ответ явно это помечает — агент не должен считать, что увидел всё.

**Обзор поверх** (`gc_search` + `gc_targets`): «покажи мои таблицы» — поиск по Drive по имени, папке, дате изменения; плюс реестр целей с алиасами и схемами колонок, откуда сразу видно, что можно писать и в каком формате. Итог: агент сначала видит **где что лежит**, потом **как устроена** таблица, и только потом читает данные.

Это видимость **одного файла**. Обзор и анализ множества файлов — Диск, расшаренное, общие диски, локальные папки — отдельный контур со своей воронкой и бюджетом, §9.

Всё прочитанное — недоверенные данные, а не инструкции (§11.6).

## 8. Понимание таблицы: резолв имён и уточнение вместо догадки

Требование: агент понимает, **что** в таблице написано и какие там колонки, а если ты сослался на колонку или значение неточно — **уточняет, опираясь на то, что реально есть**. Это не «умная модель разберётся»: см. D-7 — логика детерминированная и живёт в core.

### 8.1 Профиль колонки — что именно core знает о таблице

Карта (§7) для каждой колонки несёт не только имя, но выведенный профиль:

- **фактический тип** по данным: дата (с распознанным форматом), число, текст, ссылка, чекбокс;
- **список допустимых значений** — в первую очередь из `dataValidation` таблицы (выпадающие списки Google — авторитетный источник, не догадка), иначе по факту: если в колонке 6 уникальных значений на 300 строк, это enum, и core знает его словарь с частотами;
- **кардинальность и заполненность** — сколько уникальных, сколько пустых;
- **флаг «колонка формульная»** — критично: запись значения в формульную колонку затирает формулу. Такая запись **блокируется** и требует явного подтверждения;
- **защищённые диапазоны** (`protectedRanges`) — писать нельзя, сообщается сразу, а не после ошибки API;
- **единицы и формат** — чтобы «2ч» и «2» не превращались в мусор.

Профиль строится из одного `spreadsheets.get` с нужными полями плюс выборка строк, кэшируется на сессию и инвалидируется по `revisionId`.

### 8.2 Лестница резолва: от молча к вопросу

Когда ты говоришь «запиши 3 часа в Затрачено», а колонка называется «Часы», core проходит ступени:

| Ступень | Пример | Поведение |
|---|---|---|
| 1. Точное совпадение | `Часы` → `Часы` | молча |
| 2. Нормализация | `часы `, `ЧАСЫ`, `Ё/Е`, двойные пробелы, латинская `c` в кириллическом слове | молча |
| 3. Словарь алиасов из реестра | `Затрачено` → `Часы` (алиас подтверждён ранее) | молча |
| 4. Нечёткое, один явный кандидат | `Статус проекта` → `Статус` | **записывается, но проговаривается в превью:** «трактую „Статус проекта“ как колонку „Статус“» |
| 5. Несколько близких кандидатов | `Дата` при наличии `Дата начала` и `Дата сдачи` | **`needs_clarification`** — вопрос со списком |
| 6. Ничего похожего | `Бюджет`, а такой колонки нет | **`needs_clarification`** — вопрос + полный список колонок; создавать колонку молча запрещено |

Ключевое правило: **неоднозначность никогда не разрешается тихо**. Ни «возьму первое похожее», ни «упаду с ошибкой» — оба варианта плохие. Первый портит данные, второй возвращает тебя к ручной работе.

### 8.3 То же для значений, не только для имён

- **Enum:** пишешь `в работе`, допустимо `В работе / Готово / Пауза` → регистр правится молча (ступень 2). Пишешь `почти готово` → вопрос со списком допустимых, потому что это не опечатка, а новое значение; добавить его можно, но явно.
- **Даты:** `сегодня`, `вчера`, `1 сентября` → нормализуются в формат колонки, результат виден в превью.
- **Числа:** `3ч`, `3,5`, `3.5` → в число по формату колонки; `много` → вопрос.
- **Ключ строки не найден:** пишешь в проект, которого в таблице нет → вопрос «создать новую строку или ты имел в виду вот эти похожие?», с списком похожих значений ключа.

### 8.4 Контракт ответа инструмента

`gc_apply` возвращает одно из трёх, а не строку с текстом ошибки:

```
{ status: "ok",       applied: [...], revisionId }
{ status: "preview",  plan: [...], assumptions: ["«Статус проекта» → колонка «Статус»"] }
{ status: "needs_clarification",
  questions: [ { field: "Затрачено", reason: "no_match",
                 candidates: ["Часы", "Часы (план)"], available: [...все колонки...] } ] }
```

Типизированный ответ — то, что делает поведение одинаковым у любого провайдера: агент обязан показать вопрос человеку, а не изобретать обход. Ответ на вопрос идёт следующим вызовом.

### 8.5 Алиасы накапливаются, но только с подтверждения

Если ты подтвердил, что `Затрачено` — это `Часы`, core предлагает записать алиас в реестр цели (`aliases` в схеме, §5). Дальше это ступень 3, то есть молча. Автоматически, без подтверждения, алиасы не появляются — иначе одна случайная догадка закрепится навсегда.

## 9. Сканирование и анализ: от одного файла к корпусу

Второе назначение проекта, равное по важности записи: агент **видит и анализирует** — текст документов, листы таблиц, файлы на Диске, включая расшаренные. Не «прочитай всё и подумай» (это не влезает в контекст и стоит дорого), а воронка из четырёх ступеней с кэшем. Разделение труда — D-9: core собирает факты механически, модель интерпретирует выжимку.

### 9.1 Воронка

```
1. Инвентарь   Drive files.list -> id, имя, тип, папка, владелец, modifiedTime, размер
               (дешёво, сотни файлов; ничего не открывается)
2. Карта       по каждому отобранному файлу — структура (§7): листы, usedRange,
               заголовки, оглавление документа. Десятки строк на файл
3. Выборка     точечное чтение: нужные диапазоны, нужные разделы, N строк выборки
4. Свод        факты -> локальный индекс (JSON) -> отчёт/ответ; модель работает с индексом
```

Фильтр между ступенями — обязателен: на 2-ю ступень идут не все файлы, а отобранные по инвентарю (папка, тип, дата, имя, автор). Инвентарь на 500 файлов — норма; карта на 500 файлов — уже нет.

### 9.2 Область поиска: Мой диск, расшаренное, общие диски, локальные папки

- `myDrive`, `sharedWithMe`, `sharedDrives` (конкретный или все), папка по ID, рекурсивно или нет.
- **Технический капкан, который стоит отдельного упоминания:** для общих дисков и расшаренного нужны `supportsAllDrives=true`, `includeItemsFromAllDrives=true` и `corpora=allDrives`. Без них API молча возвращает неполный список — не ошибку, а «ничего не найдено». Это источник ложного вывода «файлов нет».
- **Локальные папки** — тот же интерфейс через провайдер `local`: инвентарь по файловой системе, карта для `.md/.csv/.xlsx/.json`, выборка. Одна воронка на Диск и на диск, чтобы «просканируй проекты» работало одинаково.
- Не-Google форматы на Диске: `.docx/.xlsx/.csv` читаются через конвертацию (`files.copy` с целевым mime или `files.export`), PDF — только если есть текстовый слой; OCR в scope не входит.

### 9.3 Что анализируется в таблице

- **Все листы**, а не первый: роль каждого (данные / отчёт / черновик), размер, дата изменения.
- **Автоопределение строки заголовков** — не всегда строка 1: в живых таблицах сверху бывает заголовок-название, пустые строки, объединённые ячейки. Core ищет строку заголовков эвристикой (заполненность, уникальность, тип последующих строк) и **показывает, что выбрал**, чтобы это можно было поправить.
- Несколько таблиц на одном листе, объединённые ячейки, ломающие разбор — детектируются и сообщаются, а не молча искажают результат.
- Профиль колонок (§8.1): типы, enum, формульные колонки, заполненность, дубли по ключу.
- **Находки уровня качества данных:** пустоты в обязательных колонках, дубли ключа, битые формулы (`#REF!`, `#N/A`), расхождение типов внутри колонки, ссылки на удалённые листы, расхождение ключей между листами, устаревшие строки.

### 9.4 Что анализируется в документе

- Оглавление H1–H6, объём, таблицы внутри документа, ссылки, изображения.
- **Tabs** документа — читаются с `includeTabsContent`; без этого параметра часть содержимого просто не видна (для проекта, выросшего из `Gdocs-tabs editor`, это критично).
- Открытые комментарии и предложенные правки (suggestions) — часто именно они и есть предмет анализа.
- Смысловая часть — на модели: о чём документ, чего не хватает, что противоречит другому документу.

### 9.5 Кэш, инкрементальность, стоимость

- Кэш карты и профиля по `revisionId` (Google-файлы) и `md5Checksum`/`mtime` (локальные и бинарные). Повторный скан не перечитывает неизменившееся.
- **Инкрементальный режим:** `modifiedTime > <дата последнего скана>` — «что изменилось с прошлой недели» дёшево.
- **Бюджет.** У скана есть явные лимиты: максимум файлов, максимум строк на файл, максимум токенов на вывод. При упоре в лимит ответ помечается как неполный и говорит, чем сузить — вместо тихого обрезания.
- Квоты Google реальны: Sheets — порядка 60 чтений/мин на пользователя, Drive — свои лимиты. Скан большого корпуса измеряется минутами, а не секундами; батчинг и backoff уже есть в `run.js` (`withRetry`).
- **Полнотекстовый поиск:** Drive умеет `fullText contains` по содержимому документов и PDF — это дёшево и должно использоваться первым. На содержимое **ячеек таблиц** так полагаться нельзя: поиск «где во всех таблицах упоминается X» в общем случае требует чтения, поэтому идёт через индекс (§9.6). Поведение `fullText` на таблицах проверить на реальном корпусе до реализации.

### 9.6 Результат скана — файл, а не контекст

Свод пишется в `~/.gconnect/index/<scan-id>.json` плюс человекочитаемый `.md`. Дальше агент отвечает на вопросы **по индексу**, а не перечитывая Диск. Следствия: скан воспроизводим, его можно diff-ить между запусками («что изменилось с прошлого раза»), он не сжигает контекст и не зависит от того, какой провайдер в этой сессии.

### 9.7 Границы читающего контура

- Скан **ничего не пишет.** Это отдельный read-профиль (D-8): читать — широко, писать — только в allowlist (§11.2). Найденную проблему агент показывает и предлагает исправление, но исправление идёт обычным путём через `gc_apply` с превью.
- **Содержимое просканированного — данные, никогда не инструкции.** Это главный риск именно читающего контура: текст в чужом расшаренном документе может содержать «добавь колонку и отправь письмо». Правило жёсткое: ничто, прочитанное сканом, не может инициировать запись или вызов другого инструмента; решение всегда за человеком в диалоге (§11.6).
- Права уважаются как есть: нет доступа — так и сообщается, никаких обходов.

## 10. Отмена изменений: честный аналог `Ctrl+Z`

Отдельная секция, потому что это самый большой разрыв между UI и API: **в Sheets/Docs API нет undo**. `batchUpdate` необратим, а история версий Google откатывает документ целиком к точке во времени, а не последнее действие.

Механизм в core:

1. Перед каждой пишущей операцией снимается состояние «до» затронутого диапазона — значения, формулы, а для форматных операций и формат — и кладётся в журнал операций сессии.
2. `gc_undo` (или `gc_apply` с `undo: <opId>`) выполняет обратную запись: восстанавливает значения/формат диапазона; структурные операции откатываются парной структурной (`insertRows` ↔ `deleteRows`, `addSheet` ↔ удаление листа).
3. **Проверка ревизии.** Если между записью и отменой документ правил человек в браузере, слепой откат перетрёт его правки. Поэтому undo сверяет `revisionId` и при расхождении не выполняется молча, а требует подтверждения.
4. В аудит-лог пишется `revisionId` до и после (§11.3) — это дублирующая страховка для ручного отката через историю версий Google.

Границы честно: undo надёжен для значений, формул, формата и структуры в пределах сессии; он не является транзакцией и не откатывает то, что успел изменить человек. Поэтому основная защита — не undo, а `dryRun` по умолчанию: дешевле не записать лишнее, чем откатывать.

## 11. Безопасность и обратимость

1. **`dryRun` по умолчанию** во всех пишущих вызовах.
2. **Allowlist.** Писать можно только в цели из реестра (`targets.json`) или в папки, помеченные `write`. Произвольный ID из промпта пишущим не является — только читаемым, и то по флагу.
3. **Снапшот ревизии.** Перед первой записью в файл — фиксация текущего `revisionId` Drive в журнал, чтобы был откат руками.
4. **Аудит-лог.** Каждая запись: время, профиль, target, ops, ревизии до/после — в `~/.gconnect/audit/YYYY-MM.jsonl`.
5. **Креды вне рабочих папок.** `~/.gconnect/<account>/{credentials,token}.json`, `chmod 600`. Ни `credentials.json`, ни `token.json` больше не лежат в папках проектов и не копируются вместе с ними.
6. **Prompt injection.** Содержимое документов — недоверенные данные. Текст из Doc никогда не трактуется как инструкция; `gc_read` помечает вывод как данные. Google в своей документации по MCP отмечает этот же риск как основной.
7. **Scopes.** MVP: `drive`, `drive.file`, `documents`, `spreadsheets`. `forms.body.readonly` — убрать до момента, когда Forms реально понадобятся (лишний scope = лишняя площадь). Смена набора scopes требует удаления `token.json` и повторного входа.

## 12. Подключение: клиенты и мозги

Ядро не знает, какая модель им управляет, и не должно знать (D-11). Три режима работы — один core, одни инструменты, одни правила:

```
                       ┌─────────────── policy/ (§12.4) ───────────────┐
                       │        правила работы с документами           │
                       └───────┬───────────────┬───────────────┬───────┘
  A. агент в чате/IDE          │               │               │
     Claude Code, Cursor,   MCP stdio          │               │
     Claude Desktop  ──────────┤               │               │
                               │               │               │
  B. локальная модель          │          agent-runner         │
     Ollama на этой машине ────┼──────────────►│               │
                               │          (свой цикл:         │
  C. любой провайдер           │           план → вызов →      │
     по API-ключу ─────────────┴──────────► проверка → отчёт)  │
                                               │               │
                                          ┌────▼───────────────▼────┐
                                          │  core: gc_read / gc_scan │
                                          │  gc_apply / gc_undo …    │
                                          └──────────────────────────┘
```

### 12.1 Режим A — агент в чате и в IDE (это и есть работа со мной здесь)

MCP stdio-сервер, модель живёт у клиента. Один и тот же сервер, разные конфиги:

- **Claude Code / Cursor / VS Code** — `.mcp.json` или `claude mcp add`, команда `node dist/mcp/server.js --profile default`.
- **Claude Desktop** — тот же stdio-сервер в `claude_desktop_config.json`.
- **Локальные папки:** в Cursor и Claude Code файловый доступ уже есть. Claude Desktop — filesystem-MCP плюс договорённость об inbox/outbox.
- Тонкий Skill поверх MCP для Claude-клиентов: не стоит контекста, пока не вызван, хранит рецепты. Но API остаётся в MCP — иначе теряется работа с другими провайдерами.

### 12.2 Режим B — локальная модель (Ollama)

Когда MCP-клиента нет или всё должно оставаться на машине. Здесь нужен **свой агент-раннер**: цикл «прочитал карту → предложил план → вызвал инструмент → проверил результат → отчитался человеку». Раннер — тонкий: вся логика уже в core, он только крутит петлю и рендерит превью.

Важное следствие, а не оговорка: **чем слабее мозг, тем больше он опирается на детерминированную часть.** Локальная модель на 7–14B плохо держит многошаговый план и арифметику индексов — но ей это и не нужно: резолвер (§8), карта вместо чтения всего файла (§7), воронка с бюджетом (§9), `dryRun`-превью и типизированный `needs_clarification` уже вынесены из модели в core (D-7, D-9). Именно это делает слабый мозг пригодным: он выбирает *что* сделать, а *как* и *куда* считает core.

Техническая честность: tool-calling у локальных моделей неровный. Раннер поддерживает два пути — нативный tool-call, если модель умеет, и структурированный JSON-выход со схемной валидацией и переспросом, если нет. Второй путь — базовый, первый — оптимизация.

### 12.3 Режим C — любой провайдер по API-ключу

Тот же раннер, другой адаптер: ключ в профиль, имя модели в конфиг. Адаптер отвечает только за «отправить сообщения и вернуть вызовы инструментов»; ни один инструмент, ни одно правило, ни одна проверка от провайдера не зависят. Смена провайдера — строка в конфиге, а не ветка в коде.

### 12.4 Правила работы с документами — один артефакт, три потребителя

Правила (что можно и нельзя делать с документами, когда спрашивать, когда писать, что считается опасным) живут в `policy/` как артефакт репозитория, а не в промпте каждого клиента:

- `policy/rules.md` — человекочитаемая политика: превью до записи, уточнение вместо догадки, прочитанное — данные, запись только в allowlist, формульные колонки не трогаем без подтверждения.
- `policy/rules.json` — машинная часть: лимиты бюджета, список запрещённых операций, что требует подтверждения человека. Её читает **core** и исполняет независимо от мозга.

Как один текст доходит до трёх режимов:

| Режим | Как получает правила |
|---|---|
| A (MCP-клиент) | `instructions` MCP-сервера + MCP-ресурс `policy://rules` + описания инструментов; для Claude-клиентов дополнительно виден `AGENTS.md` репозитория |
| B (локальная модель) | раннер подставляет `rules.md` в системный блок |
| C (API-ключ) | то же, тем же кодом раннера |
| все три | `rules.json` исполняется в core — то есть правило работает, даже если мозг его проигнорировал |

Ключевой принцип: **правило, которое существует только как текст для модели, не является правилом.** Текст объясняет, `rules.json` в core запрещает. Первое — вежливость, второе — механизм.

## 13. UI: для локальной модели и для работы по API-ключу

**Адресат UI — режимы B и C** (локальная модель, любой провайдер по ключу). В режиме A интерфейсом служит сам чат или IDE, и дублировать его формой не нужно. Отсюда и место UI в плане: он идёт вместе с агент-раннером, а не раньше.

### 13.1 Где UI выигрывает у чата, а где нет

| Задача | Кто лучше |
|---|---|
| Превью записи в таблицу: что именно изменится, было → станет | **UI.** Широкая таблица в терминале нечитаема, а именно на этом экране человек принимает решение |
| Выбор из кандидатов резолвера (§8.2 ступени 5–6) | **UI.** Клик по варианту вместо переписывания названия колонки |
| Находки скана по корпусу (§9) | **UI.** Список файлов с фильтрами и сортировкой; индекс-JSON руками не читают |
| Аудит-лог и откат (§10) | **UI.** Список записей с кнопкой «откатить» — это ровно табличная задача |
| Реестр целей, allowlist, схемы-оверлеи (§5) | **UI.** Редактировать JSON руками — гарантированные опечатки |
| Профили, OAuth, состояние scopes | **UI.** Небольшая страница «подключить аккаунт» и статус токена |
| Сформулировать задачу, обсудить формулировки, решить что писать в отчёт | **Чат.** Это диалог; форма его не заменяет и дублировать его не надо |

Вывод: UI закрывает **показ и подтверждение**, чат закрывает **замысел**.

**Но в режимах B и C чата нет — значит панель обязана содержать его сама.** Это не «показывалка результатов», а полный attended-контур (D-5) в одном окне: поле ввода задачи, поток шагов раннера, превью с диффом, уточняющий вопрос кандидатами, кнопки «применить / уточнить / отменить», история с откатом. Иначе локальная модель окажется без человека в петле — ровно то, что D-5 запрещает.

Практическое следствие для раннера: он не «печатает в консоль», а отдаёт события (шаг плана, вызов инструмента, превью, вопрос) — панель их рендерит, CLI печатает то же самое текстом. Один поток событий, два потребителя.

### 13.2 UI — фасад, а не второе ядро

Локальный HTTP-фасад ядра (bind строго `127.0.0.1`), и **два клиента одного API**: агент-раннер (§12.2–12.3) и UI. UI не содержит логики: он рендерит то, что core уже отдаёт типизированным — `preview`, `needs_clarification`, карту (§7), индекс скана (§9.6), аудит-лог. Любая логика, попавшая в UI, немедленно расходится с поведением режима A.

```
core ──► http/ (127.0.0.1) ──┬──► agent-runner (мозг B/C)
                             └──► UI (браузер)
        mcp/  ───────────────────► клиент в чате/IDE (режим A)
```

### 13.3 Три ступени

- **Ступень 0 — HTML-отчёт файлом.** Дёшево и работает уже в режиме A, без всякого UI-стека: core рендерит превью записи и отчёт скана в самодостаточный HTML-файл, агент отдаёт ссылку. Закрывает большую часть боли «покажи, что изменится» и «покажи, что нашёл». Делается вместе с фазой 2.
- **Ступень 1 — локальная панель.** React + Vite + TS + Tailwind (тот же стек, что во `local-web-agent`), прод-статика отдаётся тем же HTTP-фасадом. Вместе с раннером (фаза 4), потому что там она обязательна: очередь превью с кнопками «применить / уточнить / отменить», аудит-лог с откатом, реестр целей, статус профилей.
- **Ступень 2 — живые обновления.** SSE-прогресс на долгих сканах, отмена на полпути. Только по фактическому спросу, не заранее.

### 13.4 Границы

- **UI не получает прав больше ядра.** Кнопка «применить» — это тот же `gc_apply` с `dryRun: false`, тот же allowlist, тот же аудит (§11).
- **Только `127.0.0.1`**, никакого выставления наружу; ни одного порта, слушающего мир.
- **UI не хранит и не показывает креды.** Он спрашивает core о состоянии профиля; токены остаются в `~/.gconnect/` (§11.5).
- UI не становится обязательным звеном: любой сценарий должен проходить и без него, из чата и из CLI. Иначе панель превращается в единственную точку отказа.

## 14. Пример сценария: конец рабочего дня

**Это иллюстрация к D-5, а не часть ядра.** Никакого `daily-log` в коде нет: ядро универсально (D-10), а рецепты появятся позже, когда сценарии устоятся. Раздел оставлен как проверка, что контракты §3–§9 покрывают живой сценарий целиком.

Решение D-5: **крона нет**. Итог дня инициируешь ты, потому что «что писать в отчёт» — это содержательное решение, а не заполнение полей по шаблону. Роль агента — снять с тебя механику, но не решение.

Поток:

```
ты: «собираем итог дня»
  1. агент собирает черновик фактов        (git-коммиты за сутки по рабочим репозиториям,
                                            заметки из inbox-файла, контекст сессии)
  2. gc_read map -> видит daily-log:        какие колонки есть, что уже записано за сегодня
  3. показывает превью строки:              Дата | Проект | Статус | Часы | Комментарий
  4. вы правите вместе в диалоге:           формулировки, часы, что вообще стоит фиксировать
  5. gc_apply { op: upsertRow, dryRun: false }
```

Что остаётся из прежнего плана и почему:

- **`upsertRow` по ключу `(Дата, Проект)`** — по-прежнему обязателен (§5). Не из-за крона, а потому что в attended-режиме ты вернёшься к той же строке вечером ещё раз: дописать, уточнить часы, поправить статус. Строка за день должна быть одна.
- **Сбор фактов** из git и заметок — полезен и здесь: он экономит именно механику, оставляя решение тебе.
- **Догон пропущенного дня** — просто указываешь дату в диалоге, тем же `upsertRow`.

Что убрано сознательно: `launchd`-задача, требование «работать без интерактивного OAuth», уведомления о падении крона. Всё это существовало только ради unattended-контура, которого нет. Облачные routines (`schedule`) тем более не подходят — у них нет доступа ни к локальным кредам, ни к тебе в диалоге.

Позже, когда рецепт устоится, шаг 1 удобно завернуть в короткую команду (skill в Claude Code, `gc_preset` в остальных клиентах) — но именно как заготовку черновика, а не как автозапись.

## 16. План работ

- **Фаза 0 — гигиена (до кода).** Выбрать канонической копией `SEO:Content/Gdocs-tabs editor` (она самая полная: 16 плагинов, `lib/validators`, `exports`). Две другие копии — заморозить. **Перевыпустить Telegram bot token и вынести все секреты из рабочих папок**: `credentials.json` / `token.json` / токены переезжают в `~/.gconnect/<account>/` с `chmod 600` (§10.5).
- **Фаза 1 — core.** `auth` + `profiles` + `targets` + `retry` + примитивы Docs/Sheets/Drive, портированные из `run.js` под схему `ops.ts`. Сразу с ними — карта заголовков, `appendRow` / `upsertRow` / `setCells`, валидация по схеме таблицы (§5) и **резолвер колонок и значений** (§8): это несущая часть, а не надстройка. Тесты на схемы операций, пересчёт селекторов, идемпотентность upsert и на все шесть ступеней резолва.
- **Фаза 2 — MCP.** Шесть инструментов, stdio, `policy/` и отдача правил как ресурса (§12.4), HTML-превью и отчёт скана файлом — UI ступени 0 (§13.3), `dryRun` по умолчанию, аудит-лог, карта документа (§7), резолвер колонок (§8) и `gc_undo` (§10). Проверка на Cursor и Claude Desktop.
- **Фаза 2.5 — паритет с горячими клавишами.** Дописать пробелы из §6.2: `underline`, `align`, `insertRows/Columns`, `deleteRows/Columns`, `addSheet`, `copyRange/cutRange` (в т.ч. вставка только значений), `autoFill`.
- **Фаза 2.7 — читающий контур.** `gc_scan`: инвентарь по Диску / расшаренному / общим дискам / локальным папкам, карта, автоопределение строки заголовков, базовые `checks`, индекс и инкрементальный режим (§9).
- **Фаза 3 — CLI и сбор черновика итога дня.** `actions.json` и пресеты работают через тот же core; рецепт сбора фактов за день (§14) — запускаемый тобой, не по расписанию; старый `run.js` выводится из эксплуатации.
- **Фаза 4 — агент-раннер + UI ступени 1 (режимы B и C).** Локальный HTTP-фасад на `127.0.0.1`; панель на React + Vite + TS + Tailwind (D-14), прод-статика с того же фасада: очередь превью, аудит с откатом, реестр целей, профили (§13.3). Режимы B и C: цикл раннера, адаптеры `ollama` и `openai-compatible`/`anthropic`, подстановка `policy/rules.md`, путь со структурированным JSON-выходом для моделей без нативного tool-calling (§12.2–12.3). UI ступени 0 (HTML-отчёт файлом) к этому моменту уже есть с фазы 2.
- **Фаза 5 — расширения** по таблице §15, в порядке реального спроса.

Критерий готовности MVP — шесть сценариев:
1. **Видит.** «Покажи мои таблицы» → список; «что в этой таблице» по любой ссылке → карта листов, колонок и примеров строк, без вываливания тысяч строк в контекст и без предварительной настройки.
2. **Пишет вместе.** Из Claude Desktop и из Cursor одинаковой формулировкой («допиши это в таблицу по колонкам», «поправь H2 в документе») получается один и тот же корректный результат на **произвольной** таблице: превью → правки в диалоге → запись → аудит-лог. Повторный вызов с тем же ключом правит ту же строку, а не создаёт новую.
3. **Понимает и уточняет** — на таблице, которую видит впервые. Ошибка в названии колонки («Затрачено» при колонке «Часы») → близкий кандидат проговаривается в превью; «Дата» при двух датах в таблице → вопрос со списком; несуществующая колонка → вопрос, а не тихая запись мимо и не падение. Значение вне enum → вопрос с допустимыми. Запись в формульную колонку блокируется.
4. **Сканирует.** «Пройди по папке на Диске и скажи, где в таблицах пустые обязательные поля и дубли ключей» → инвентарь, карта, проверки, свод в файл-индекс, ответ по индексу; повторный запуск через неделю показывает разницу. Расшаренные файлы и общие диски попадают в выдачу, локальные папки — тем же вызовом.
5. **Не зависит от мозга.** Один и тот же сценарий проходит из чата/IDE через MCP и через раннер с локальной моделью: инструменты, правила и проверки те же, различается только качество формулировок. Правило из `rules.json` срабатывает даже если модель его проигнорировала.
6. **Откатывает.** Ошибочная запись снимается `gc_undo` в пределах сессии, а при правках человека в браузере откат не выполняется молча (§10.3). Всё из чек-листа §6.1–6.2 доступно как операция.
