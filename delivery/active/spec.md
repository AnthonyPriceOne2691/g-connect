# Spec: ядро (фаза 1) — профили, ошибки, примитивы Sheets, резолвер

Источник правды по архитектуре — [DESIGN.md](../../DESIGN.md). Здесь только то, что
входит в **фазу 1**, и наблюдаемые критерии к ней.

## Problem

Существующий движок (`Gdocs-tabs editor`, ~2800 строк на Node) умеет всё нужное, но его
интерфейс — файловый батч: агент должен писать JSON в файл и просить запустить npm-скрипт.
Плюс он размножен в трёх папках с кредами внутри. Нужно ядро, которое можно вызывать
как библиотеку (дальше — из MCP, CLI и раннера), работающее с **произвольной** таблицей
без предварительной настройки.

## Users / stakeholders

Владелец проекта (единственный пользователь на этой фазе). Потребители кода — фаза 2 (MCP)
и фаза 4 (раннер и панель).

## In scope

- `profiles` — раскладка `~/.gconnect/<account>/`, чтение `credentials.json`/`token.json`, права 600.
- `errors` — типизированные ошибки с `code`/`title`/`retryable`/`action` (§13.7, D-15).
- `retry` — backoff на 429/5xx (порт из `run.js`).
- `targets` — резолв цели: alias из реестра, URL, ID; тип по URL (doc/sheet).
- `sheets` — карта листа: листы, `usedRange`, автоопределение строки заголовков, профиль колонок; чтение значений; `appendRow` / `upsertRow` / `setCells` по именам колонок.
- `resolver` — шесть ступеней резолва имени колонки и нормализации значения (§8.2, §8.3).
- `ops` — схема операций (zod) с `dryRun` и планом изменений.
- `auth` — OAuth-вход и обновление токена (реальный сетевой путь; проверяется человеком).

## Out of scope

- MCP-сервер и CLI (фаза 2 и 3), панель и раннер (фаза 4).
- Docs-примитивы и селекторы по тексту (фаза 2 — идут вместе с MCP).
- `gc_scan` и корпусные проверки (фаза 2.7).
- Копирование/автозаполнение и прочие пробелы паритета (фаза 2.5).
- Любая привязка к конкретным таблицам (D-10).

## Acceptance (observable)

- [ ] Ни одного имени листа, колонки или таблицы в коде ядра (проверяется грепом).
- [ ] Все записывающие операции по умолчанию возвращают план, а не пишут.
- [ ] Ошибка любого класса из §13.7 несёт `title` на русском и `action`.
- [ ] `npx tsc --noEmit` и `npx vitest run` зелёные.

## Acceptance examples

Таблица-фикстура «Лист1» (используется во всех примерах):

| | A | B | C | D |
|---|---|---|---|---|
| **1** | Отчёт за сентябрь | | | |
| **2** | Дата | Проект | Статус | Часы |
| **3** | 2026-09-01 | G connect | в работе | 2 |
| **4** | 2026-08-31 | lash-try-on | готово | 5 |

Колонка `Статус` имеет `dataValidation` со списком `в работе / готово / пауза`.

| # | Вход | Ожидаемый выход |
|---|---|---|
| A1 | карта листа по фикстуре | `headerRow: 2` (не 1), `usedRange: A1:D4`, колонки `Дата`(date) `Проект`(string) `Статус`(enum: в работе\|готово\|пауза) `Часы`(number), 2 строки данных |
| A2 | `upsertRow` ключ `{Дата: 2026-09-01, Проект: G connect}`, значения `{Часы: 3}` | план: изменить `D3` с `2` на `3`; новых строк 0; после `dryRun:false` — в таблице 2 строки данных, не 3 |
| A3 | `upsertRow` ключ `{Дата: 2026-09-02, Проект: G connect}`, значения `{Статус: готово, Часы: 1}` | план: добавить строку 5 со значениями по колонкам; после записи — 3 строки данных |
| A4 | `setCells` `where {Проект: G connect}`, значения `{Статус проекта: готово}` | `status: preview`, `assumptions: ["«Статус проекта» → колонка «Статус»"]` — ступень 4, пишет, но проговаривает |
| A4b | то же со `{Затрачено: 4}` при `aliases: {Часы: [затрачено]}` в реестре | записано в `Часы` молча, `assumptions` пусты — ступень 3, подтверждённый алиас |
| A4c | то же со `{Стаус: готово}` (опечатка) | `preview` с `assumptions: ["«Стаус» → колонка «Статус»"]` — ступень 4 по близости |
| A5 | `setCells` `where {Проект: G connect}`, значения `{Дата: сегодня}` при двух колонках `Дата начала`/`Дата сдачи` в другой фикстуре | `status: needs_clarification`, `candidates: ["Дата начала","Дата сдачи"]` — ступень 5, не пишет |
| A6 | `setCells` значения `{Бюджет: 100}` | `status: needs_clarification`, `reason: no_match`, `available: [Дата, Проект, Статус, Часы]`; колонка не создана |
| A7 | `upsertRow` значения `{Статус: В РАБОТЕ}` | записано `в работе` (ступень 2, регистр молча) |
| A8 | `upsertRow` значения `{Статус: почти готово}` | `needs_clarification` со списком `в работе / готово / пауза` — новое значение, а не опечатка |
| A9 | `upsertRow` значения `{Часы: 3ч}` | записано число `3` (нормализация по типу колонки) |
| A10 | `setCells` в колонку, содержащую формулу | `write_blocked`, `title: «Писать сюда нельзя: формульная колонка»`, `action` = подтвердить осознанно |
| A11 | ключ `{Проект: Gconnect}` (нет такой строки) при существующем `G connect` | `needs_clarification`: создать новую строку или имелось в виду `G connect` |
| A12 | любой вызов при отсутствии `~/.gconnect/default/token.json` | `code: no_profile`, `title: «Аккаунт Google не подключён»`, `action: connect_google` — не «ENOENT» и не стектрейс |

## Non-functional

- Ядро не зависит от модели и от клиента (D-11): никаких импортов провайдеров.
- Секреты не выходят за `~/.gconnect/` и не попадают в возвращаемые объекты и логи.
- Один вызов карты листа — не больше одного `spreadsheets.get`; профиль кэшируется по `revisionId`.

## Open questions

- Формат `usedRange` в ответе: A1-строка или `{startRow,endRow,...}`. Решается в plan.
- Нужен ли `addColumn` уже в фазе 1 (сейчас out of scope, создание колонки только явное).
