# Spec: MCP-сервер (фаза 2) — шесть инструментов, правила, превью, откат

Архитектура — [DESIGN.md](../../DESIGN.md) §3, §12.4, §13.3. Здесь только фаза 2.

## Problem

Ядро фазы 1 вызывается только из тестов и обвязки. Агент в чате и IDE к нему не подключён:
чтобы «допиши это в таблицу» работало из Cursor и Claude Desktop, нужен MCP-сервер —
единственный интерфейс, одинаковый у любого провайдера (D-4, D-11).

## Users / stakeholders

Владелец (единственный пользователь). Потребители: Cursor, Claude Desktop, Claude Code;
дальше — раннер фазы 4 через тот же core.

## In scope

- `src/mcp/server.ts` — stdio-сервер, шесть инструментов: `gc_targets`, `gc_read`,
  `gc_apply`, `gc_undo`, `gc_search`, `gc_scan` (последний — минимально: инвентарь и карта).
- `src/core/ops.ts` — zod-схема операций на внешней границе (отложена из фазы 1 сознательно).
- `src/policy/` — `rules.md` (человекочитаемая политика) и `rules.json` (машинная часть,
  исполняется в core). Отдача правил как MCP-ресурса `policy://rules` + `instructions` сервера.
- `src/core/audit.ts` — журнал записей: время, профиль, target, операции, ревизии до/после.
- `src/core/undo.ts` — снимок «до» и обратная запись со сверкой ревизии.
- `src/core/report/html.ts` — превью записи и отчёт скана самодостаточным HTML-файлом (ступень 0).
- Сборка `dist/` (tsc emit) — сервер должен запускаться клиентом из собранного кода.

## Out of scope

- Docs-примитивы и текстовые селекторы (фаза 2.5 вместе с паритетом клавиш).
- Полный `gc_scan` с проверками качества данных и индексом (фаза 2.7).
- CLI-фасад и рецепты (фаза 3), раннер и панель (фаза 4).
- Stryker — отдельной задачей в этой же фазе, но не блокирует её acceptance.

## Acceptance (observable)

- [ ] Сервер стартует из `dist/`, отвечает на `initialize`, отдаёт ровно шесть инструментов.
- [ ] Все пишущие вызовы по умолчанию возвращают превью; запись требует явного `dryRun: false`.
- [ ] Каждое ограничение из `rules.json` имеет отказ на уровне core, а не только текст в `rules.md`.
- [ ] Ошибки уходят клиенту как `code` + `title` + `action`, без стектрейсов.
- [ ] `npx tsc --noEmit`, `npx vitest run`, все гейты pre-commit — зелёные.

## Acceptance examples

Фикстура — та же таблица из фазы 1 (шапка во второй строке, enum на «Статус»).

| # | Вход | Ожидаемый выход |
|---|---|---|
| B1 | `tools/list` | ровно 6 инструментов; у каждого непустой `description` и JSON-схема входа |
| B2 | `gc_targets` без аргументов | список целей реестра с `alias`, `type`, `allow`; секретов и путей к профилю в ответе нет |
| B3 | `gc_read {target, mode: "map"}` | карта: `headerRow: 2`, колонки с типами и enum, `sampleRows` ≤ 3, `warnings` |
| B4 | `gc_apply {op: upsertRow, key, values}` без `dryRun` | `status: "preview"`, план изменений, в таблицу ничего не записано |
| B5 | `gc_apply` с `values: {Бюджет: 100}` | `status: "needs_clarification"`, `questions[0].available` — все колонки листа |
| B6 | `gc_apply {op: "удалиВсё"}` (нет такой операции) | вызов отклонён ДО обращения к Google, в тексте перечислены допустимые операции. **Уточнено по живой пробе:** SDK валидирует вход по объявленной схеме раньше обработчика, поэтому такая ошибка приходит протокольной (`-32602`, с перечислением значений), а не типизированным payload. Схему сознательно оставляем строгой: агент видит допустимые значения в `tools/list` и не совершает ошибку вовсе |
| B6b | `gc_apply {op: "upsertRow", target: <не в реестре>, dryRun: false}` | `policy_denied` с `cause: write.allowlist` **без единого обращения к Google**: право проверяется до сети |
| B7 | `gc_apply {dryRun: false}` на цель вне реестра | `policy_denied` с названием правила из `rules.json` |
| B8 | `resources/read policy://rules` | содержимое `rules.md`; тот же текст виден в `instructions` сервера |
| B9 | запись, затем `gc_undo {last: 1}` | значения вернулись; в аудит-логе две записи с ревизиями до/после |
| B10 | `gc_undo` после правки документа человеком (ревизия изменилась) | `revision_conflict`, откат не выполнен |
| B11 | `gc_apply {dryRun: false}` | в `~/.gconnect/audit/YYYY-MM.jsonl` добавлена строка: время, профиль, target, ops, ревизии |
| B12 | `gc_read` с превью в HTML | файл создан, открывается сам по себе, содержит таблицу «было → станет»; путь возвращён в ответе |
| B13 | одна и та же формулировка из Cursor и из Claude Desktop | один и тот же результат: превью → правки в диалоге → запись (ручная проверка человеком) |

## Non-functional

- Контекст: ответ `gc_read map` — десятки строк, не тысячи; `sampleRows` ограничены.
- Инструментов ровно шесть: «не выставлять 30 мелких» (§3) — это требование, а не стиль.
- Ядро от MCP не зависит: `src/core/**` не импортирует `src/mcp/**` (гейт `layers` это судит).

## Open questions

- Формат `gc_scan` в этой фазе: только `depth: inventory|map` или сразу с `checks`.
- Нужен ли `gc_apply` батч из нескольких целей за вызов (сейчас — одна цель).
