# Plan: G connect из любого проекта — разрешение касанием пальца

Класс L: новое решение безопасности (D-23 — разрешение подписью Secure Enclave), седьмой
инструмент, изменение права записи в ядре, установка в конфиги Claude Code. Слайсы идут от изолированного к связующему: подпись и стабильная сборка не трогают
ядро, ядро меняется, когда оба механизма уже проверены.

## Slices

1. **Стабильная сборка** (`scripts/install_stable.sh`): экспорт коммита `main` (`git archive`)
   в `~/Library/Application Support/g-connect/stable` — вне репозитория (решение 2026-10-17
   в decisions.md); `npm ci`, сборка, проба протокола на собранном сервере, `npm prune
   --omit=dev`, проба ещё раз. Переключение — только при зелёной пробе. Примеры X11, X12.
2. **Разрешение: подпись и проверка** (`src/core/grant.ts`). Документ разрешения — текст
   фиксированного вида (версия, проект, область, выдано, истекает, nonce); подпись —
   `ssh-keygen -Y sign -n g-connect-grant` с `SSH_AUTH_SOCK` агента Secretive; проверка —
   `ssh-keygen -Y verify` против ключа, который отдаёт агент Secretive (`ssh-add -L`) по
   имени, выбранному на установке. Подписчик и проверяющий — внедряемые: в тестах
   программный ключ, живьём — Secretive. Хранение — `~/.gconnect/grants/<sha256 проекта>`,
   права 600. Примеры X3–X6.
3. **Право записи по разрешению.** `assertWritable` → проверка «реестр ИЛИ действующее
   разрешение проекта»; проект — `CLAUDE_PROJECT_DIR`; без него — только чтение. Под разрешением: неразрушающее — с первой фразы (как
   конверт), разрушающее — фраза + код плана; создание — в «Моём диске» (`root`), созданное
   — пишется. Журнал несёт проект; откат проверяет проект. Примеры X2, X5, X8–X10.
4. **`gc_grant` — седьмой инструмент** (поправка §3 «шесть толстых»): выдать, показать,
   отозвать; отказ без разрешения — `needs_grant` с действием. Правила: три новых
   машинных правила с пробами. Примеры X1–X3.
5. **Таблица со шапкой:** `createSheet` + `columns`/`rows`, запись текстом (`asText`, RAW).
   Пример X7.
6. **Подключение Claude Code** (`scripts/connect_claude.sh`, согласие владельца дано
   2026-10-17): сервер уровня пользователя, `mcp__g-connect__*` в `~/.claude/settings.json`,
   памятка в `~/.claude/CLAUDE.md`, резервные копии. Cursor и Codex — вне объёма. Пример X1.
7. **Живой прогон из другого проекта:** новая сессия в соседнем проекте, касание, X1–X10
   на тестовой таблице в «Моём диске», откаты, корзина.

## Rejected alternatives

- **Свой Swift-помощник с LocalAuthentication** (свой текст в окне Touch ID) — отклонён в пользу
  Secretive, потому что ключ Secure Enclave из неподписанной утилиты не хранится постоянно без
  entitlements, а простое «Touch ID прошёл» без криптографии подделывается записью файла.
- **Ключ проверки из файла `~/.gconnect/grant-signer.pub`** — отклонён, потому что агент с
  доступом к диску подменил бы его своим программным ключом и подписывал бы без пальца. Ключ берётся у
  агента Secretive, который отдаёт только ключи Secure Enclave.
- **Фраза в чате как разрешение** — отклонена, потому что проверить её может только сессия,
  где она сказана.
- **Сервер из рабочей сборки для всех проектов** — отклонён, потому что каждая недоделка ветки
  ломала бы все сессии на машине (решение 2026-10-01: «сервер из стабильной сборки main»).
- **Хук, запрещающий соседним сессиям прямой доступ к Google** — отклонён, потому что владелец
  2026-10-13 не считает прямую работу проблемой.

## Риск и порядок

Самое опасное — слайс 3: меняется ответ на вопрос «кто может писать». Поэтому он идёт
после слайса 2 (подпись проверена отдельно, в том числе подложенный файл и чужой ключ) и
с обратными прогонами каждого отказа. Второй риск — окно Touch ID из дочернего процесса
сервера: документация Claude Code об этом молчит, проверяется живьём на слайсе 7.
Третий — запись в чужие конфиги: только скриптом, с резервной копией и согласием.

## Уроки архива (INDEX: пересечение путей с диффом)

- **L6** — обещание в ответе исполняет механизм: «разрешение до 23:59» в `gc_targets`
  показывается из ПРОВЕРЕННОЙ подписи, а не из файла.
- **L7** — у каждого отказа (X2, X4–X6, X10) обратный прогон: без проверки — красный.
- **L8** — id примеров X1…X12 подписаны и не переименовываются; X1/X7 — ещё и адреса ячеек,
  поэтому в фикстурах колонку X не используем.
- **L10, L11** — новый ответ «кто может писать» краснит старые оракулы записи — переводим их,
  а не обходим; порядок «реестр → разрешение → конверт» закрепляем оракулом.
- **L12** — `CLAUDE_PROJECT_DIR` читается только в `src/core/env.ts`; каталог разрешений
  выводится из `profilesHome()`, сьют не пишет в настоящий `~/.gconnect`.
- **L15, L28** — палец проверяет только живой прогон с владельцем (X3); тесты на программном
  ключе проверяют механику, а не подпись человека, — это названо в verify-report.
- **L17** — разрешение отвечает «кто может писать», а не подтверждает каждую правку: превью,
  код плана и журнал остаются.
- **L21, L26, L27** — схема `gc_grant` из того же источника, что ядро; тесты инструмента —
  через настоящий протокол; незнакомое поле — отказ; проба считает семь инструментов.
- **L23** — подпись и проверку в тестах гоняет НАСТОЯЩИЙ `ssh-keygen` с программным ключом;
  фейк подменяет только источник ключа (агента Secretive).
- **L24** — живой прогон пишет только в таблицу, которую сам создал в «Моём диске».
- **L29** — проба не пропускает шов разрешения молча: SKIP называет, что не проверено.
- **L30** — право записи решает ОДНА функция (`authorizeWrite`): реестр и разрешение — две
  ветки одного ответа, а не два пути.
- **L14** — новое поле, которое пишет одна сторона и не читает другая: `structural.content`
  создания таблицы добавлен и в `StructuralPlan`, и в `planOf`, и в `PlanStructure` — код
  плана меняется вместе с содержимым (тест «код плана меняется вместе с содержимым»).
- **L18** — прокси в подписи: в подпись разрешения не входит ничего, что меняется само
  (ревизии, время файла); срок — поле текста, подписанное пальцем.
- **L19** — чек-лист живого прогона прочитан на порядок шагов: откат (шаг 7) стоит ПОСЛЕ
  удаления, отзыв (шаг 10) — до отката создания.
- **L5** — пустой результат называет ядро: «своих записей нет» — `only_other_projects`, а не
  «журнал пуст»; `nothing_to_revoke` у `gc_grant`.
- **L9** — область мутационного гейта — маска конфига, а не список (накат контура: фильтр
  изменённых файлов маской `stryker.config.json`).
- **L20** — гейт сложности отклонял четыре раза, каждый раз по делу (verify-report).
- **L25** — о гейте отчитываюсь прогоном `delivery_check --diff-base main`.
- **Не применимы:** L1 (свежий репозиторий), L2 (ветка с фазы 2 — здесь ветка
  `feat/cross-project`), L3 (живое чтение дат — поставка дат не читает), L4 (пункты дизайна
  без оракула — каждый новый пункт DESIGN.md этой поставки сопровождён тестом), L13
  (формулы), L16 (границы данных листа).
