# Spec: паритет с горячими клавишами, часть A — вид, формулы, поиск (фаза 2.5a)

Архитектура — [DESIGN.md](../../DESIGN.md) §6, §3, §10. Здесь только часть A: операции,
которые правят СУЩЕСТВУЮЩИЕ ячейки. Структурные (`insert*`, `delete*`, `addSheet`,
`copy*`, `autoFill`, `create*`) вынесены в 2.5b решением от 2026-09-03.

Идентификаторы примеров — **V1…V12** («вид»). История выбора важнее самого выбора: сначала
я взял двухбуквенный префикс `HK`, потому что урок **L8** учит не сталкивать id с нотацией
домена — в проекте про таблицы «буква+цифра» это адрес ячейки, и §3.1d однажды объявила
ожидания придуманными после кода, найдя в фикстуре `=B2*1`. Но `delivery_check` отклонил
спеку: канон требует id ровно вида «одна заглавная латинская буква + цифры».

Компромисс: форма канонная, а буква — та, которой нет ни в одном адресе фикстур и логов
(там встречаются A, B, C, D, F). Остаточный риск назван: если фикстура дорастёт до колонки
V, §3.1d может ложно предупредить — предупредить, не уронить. Настоящее лечение — учить
§3.1d сверять порядок по id из первой колонки таблицы примеров, как она уже делает при
разборе. Это правка канона, а не этой поставки.

## Problem

Дизайн объявляет паритет с горячими клавишами критерием полноты (D-6), а §6.2 перечисляет
девять пробелов. Чтение кода показало, что дыра шире объявленной:

1. **В новом ядре нет и базы §6.1.** `src/core/ops.ts` знает ровно три операции:
   `appendRow`, `upsertRow`, `setCells`. Ни `formatCells` (даже bold/italic/фон, которые
   §6.1 считает «уже есть»), ни `findReplace` в нём не существует — они были в старом
   `run.js`, а в ядро не переносились.
2. **Шов с библиотекой не умеет ничего, кроме значений.** `SheetsClient` — это
   `getSpreadsheet`, `updateValues`, `appendValues`. Все операции вида живут в
   `spreadsheets.batchUpdate` (`repeatCell`, `findReplace`), которого в шве нет вовсе.
3. **Ядро не видит вид ячейки.** `includeGridData: true` уже запрашивается, но `toCell`
   оставляет из ответа только `value` и `formula`; `textFormat`, `horizontalAlignment` и
   `backgroundColor` отбрасываются. Значит нечем ни показать «было → станет» для вида, ни
   положить снимок в журнал для отката.

Следствие для человека: «сделай заголовок жирным» или «выровняй столбец по правому краю»
агент выполнить не может, а «замени во всём листе X на Y» — тем более.

## Users / stakeholders

Владелец. Потребители — те же клиенты MCP; после 2.5b и фазы 3 те же операции идут из CLI
и раннера через тот же core.

## In scope

- **Шов:** `batchUpdate` в `SheetsClient` и в `GoogleSheetsClient` — один метод, принимающий
  доменные запросы, а не типы `googleapis` (иначе фейк в тестах придётся строить под форму
  библиотеки — решение фазы 1).
- **Вид в снимке:** `Cell.format` — `bold`, `italic`, `underline`, `align`
  (`left|center|right`), `background`. Мэппинг в `toCell`, домен в `sheets/types.ts`.
- **Операция `formatCells`:** адресация как у `setCells` — по ключу строки и именам колонок
  (или по всей колонке), поля вида задаются частично: `{ bold: true }` не сбрасывает
  остальное.
- **Операция `findReplace`:** по листу или диапазону, с `matchCase`, `matchEntireCell`,
  `searchByRegex`; в превью — список затрагиваемых ячеек с «было → станет», а не «заменено N».
- **Формулы:** отдельной операции НЕ добавляется. `updateValues` уже пишет с
  `valueInputOption: USER_ENTERED`, то есть значение `=B2*1` попадает формулой; это
  проверяется примером V9, а в `rules.md` появляется абзац, что формула — это значение,
  начинающееся с `=`, и она подчиняется тому же правилу `write.formula-column`.
- **Подтверждение и откат для вида:** правка вида проходит тот же контур D-16/D-17 —
  код плана, предусловие, журнал, `gc_undo`. Снимок формата «до» кладётся в журнал (решение
  от 2026-09-03).
- **Правила:** `write.format-preserves-values` (правка вида не меняет значений),
  `write.replace-preview-lists-cells` (замена показывает ячейки, а не число).

## Out of scope

- Структурные операции и создание файлов — 2.5b.
- Docs-примитивы и текстовые селекторы — остаются за §15 (`gc_comment`), не здесь.
- Условное форматирование, объединение ячеек, границы, числовые форматы — §6.2 их не
  требует; появятся по спросу (§15).
- Полный `gc_scan` — 2.7.

## Acceptance (observable)

- [ ] Все операции вида и замены проходят через `gc_apply` с тем же контуром: превью с кодом
      плана, запись только по коду, строка журнала, работающий `gc_undo`.
- [ ] Правка вида не меняет ни одного значения, и на это есть оракул, а не обещание.
- [ ] Превью замены перечисляет затрагиваемые ячейки с «было → станет».
- [ ] Каждое новое правило имеет `enforced_in` на существующий файл и пробу.
- [ ] Шов с библиотекой остаётся один: `batchUpdate` живёт только в `src/core/google/`,
      гейт `core-no-library` это судит.
- [ ] `npx tsc --noEmit`, `npx vitest run`, smoke S0–S11, все хуки pre-commit — зелёные.

## Non-functional

- **Контекст.** Карта не толстеет вдвое: `format` попадает в профиль колонки одной строкой
  и только когда отличается от значения по умолчанию.
- **Один шов.** `batchUpdate` принимает доменные структуры; типы `googleapis` не протекают
  в `src/core/sheets/**` — на это есть гейт.
- **Снимок формата — только затрагиваемые ячейки.** Не лист и не строка: журнал не должен
  расти пропорционально размеру таблицы.

## Open questions

- **Гранулярность `findReplace`.** Google умеет заменить одним запросом, но тогда «было →
  станет» по ячейкам придётся собирать чтением ДО (лишний запрос). Альтернатива — заменять
  через `updateValues` по найденным ячейкам, тогда превью бесплатно, но операция перестаёт
  быть атомарной. Предлагаю второе: атомарность здесь дешевле честного превью, а превью —
  ядро всего контура.
- **`align: "justify"`** в Sheets есть, в §6.2 не назван. Предлагаю не добавлять, пока не
  попросят: каждое поле вида это ещё одна ветка в снимке и в откате.
