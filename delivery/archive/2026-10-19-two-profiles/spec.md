# Spec: два профиля рядом — личный и второй аккаунт Google в одной сессии

Архитектура — [DESIGN.md](../../DESIGN.md) D-23 (разрешение проекта касанием), D-24 (токен под
пальцем); эта поставка вводит **D-25**. Открыта словом владельца 2026-10-19: «рабочий и
личный должны быть рядом» — и выбором порядка «Мерж → „два профиля“ → накат»; временное
подключение вторым сервером до поставки владелец отклонил («Нет, ждать поставку»).

Идентификаторы примеров — **W1…W10** («work»; P занят примерами прошлых поставок в тестах). U — прошлая поставка (token-touch),
T — задачи (§3.1d, урок L8).

## Problem

1. **Сервер G connect работает с одним профилем, и подключение жёстко ставит личный:**
   `connect_claude.sh` регистрирует `g-connect` с `GCONNECT_ACCOUNT=default`. Второй профиль
   (`work`: свой Cloud-проект, свой ключ анклава, вход проверен чтением 2026-10-19) доступен
   только из терминала.
2. **Второй сервер рядом без доработки ломает то, что держится на «один профиль»:**
   - разрешение проекта лежит файлом на проект, а не на профиль
     (`~/.gconnect/grants/<проект>.json`): открыть его рабочему — затереть личное в том же
     проекте, и наоборот (`grants.ts` отвечает `other_account`);
   - `gc_targets` перечисляет все профили и не говорит, какой у этого сервера;
   - откат выбирает запись по проекту и цели, а не по профилю: на файле, доступном обоим
     аккаунтам, рабочий сервер откатит запись личного;
   - строка перед окном Touch ID и фраза «открой G connect» одни на оба профиля: человек не
     знает, какой Google открывает касание;
   - скрипт подключения и памятка знают один сервер.
3. **Инструкции сервера доходят до агента не целиком.** В сессии Claude Code 2026-10-19
   агенту видны первые ~5 тыс. знаков из 23 тыс.: раздел «Про доступ» (D-24, позиция ~21,6
   тыс.) — за обрезкой. Правило касания доходит описанием `gc_unlock`, ответом
   `google_locked` и памяткой, а не инструкциями (отчёт token-touch утверждал иначе —
   поправка здесь). Профиль сервера, названный в конце правил, агент не увидит.

## Users / stakeholders

- Владелец: одна машина, два аккаунта Google — личный (`default`) и второй (`work`).
- Агенты в сессиях Claude Code любого проекта: видят оба сервера и выбирают, через какой идти.

## In scope

1. **Подключение по списку профилей**, названному при подключении: `default` → сервер
   `g-connect` (как сейчас), другой профиль → `g-connect-<профиль>`; правило доступа и строка
   памятки — на каждый; ключ разрешений `irreversible` — у всех; внутри репозитория
   G connect — dev-сборка для каждого (область local, L33); `--disconnect` снимает все.
2. **Сервер знает свой профиль и называет его** первой строкой инструкций, в `gc_targets`
   (свой профиль — отдельно; о других — только имя сервера), в строке перед окном
   («G connect (work) попросит палец…») и во фразе разрешения («открой G connect (work)»).
   У `default` строка и фраза — прежние, слово в слово.
3. **Разрешение проекта — на пару «проект, профиль».** Разрешение, открытое до поставки,
   не открывает запись ни одному профилю: мигрировать нечего, срок и так до 23:59.
4. **Откат — только записи своего профиля.** Чужая запись на той же цели — отказ с именем
   сервера, которым её откатывать; файл не тронут.
5. **Памятка и правила:** какой сервер для каких файлов; «не знаешь, чей файл, — спроси
   человека»; ничего, кроме имён профилей и серверов.

## Out of scope (названо, а не забыто)

- Один сервер на оба профиля с аргументом `account` в каждом вызове — разбор в плане.
- Больше двух профилей живьём: механизм общий, живой прогон — на двух.
- Перенос и копирование файлов между аккаунтами.
- Cursor и Codex (решение владельца 2026-10-17 — только Claude Code).
- Право `gmail.send` у второго профиля — остаётся: владелец дал его при входе 2026-10-19.
- Остальные правила за обрезкой инструкций (проблема 3) — кандидат отдельной поставки;
  здесь — только то, что нужно двум профилям.

## Acceptance (observable)

Новая сессия Claude Code в соседнем проекте видит два набора инструментов; каждый сервер
называет свой профиль в начале инструкций и в `gc_targets`; касание открывает только свой
профиль; разрешение и откат одного профиля не трогают другой; отключение снимает оба.

## Non-functional

- Обратная совместимость: имя `g-connect`, правило `mcp__g-connect__*`, строка и фраза
  личного профиля — без изменений (W10); тесты и памятка D-24 остаются верными.
- Профиль — имя каталога в `~/.gconnect`; адреса, домены и названия рабочих файлов в
  репозиторий не попадают (репозиторий публичный).
- Инструменты — тестами через настоящий протокол (L26); скрипт подключения — на временном
  каталоге (`CLAUDE_HOME`, `CLAUDE_JSON`, `CLAUDE_BIN`) и живьём — только словом владельца.

## Цена — числами

- **Второй набор из восьми инструментов в каждой сессии.** Список инструментов сервера —
  13,1 тыс. знаков, инструкции — 23,3 тыс. (замер 2026-10-19). В этой версии Claude Code
  инструменты MCP отложены до первого вызова, а инструкции обрезаны до ~5 тыс. знаков —
  сверху добавляются восемь имён и ~5 тыс. знаков инструкций.
- **Касание на каждый профиль:** сессия, работающая с обоими, касается дважды в час.
- **Разрешения, открытые до поставки, перестанут действовать** — открыть заново (срок всё
  равно до 23:59).
- Оценка объёма — в плане; класс M.

## Решения владельца (вопросы с вариантами — после подписи сюда)

- 2026-10-19 · **Спека — «Подписываю»** (вопрос с вариантами; id примеров были P1…P10,
  переименованы в W1…W10 до кода — P1…P22 заняты тестами прошлой поставки; подтверждение —
  вместе с планом).
- 2026-10-19 · **Имя второго сервера — `g-connect-work`** (инструменты
  `mcp__g-connect-work__*`) вместо переименования обоих в `g-connect-personal` и
  `g-connect-work` — потому что личный остаётся `g-connect`: правило `mcp__g-connect__*` и
  памятка D-24 не ломаются.
- 2026-10-19 · **Второй сервер без запроса прав, как личный**, вместо запроса на каждый
  вызов — потому что запись и так идёт через превью, код плана и разрешение касанием, а
  Google открывается только пальцем.
