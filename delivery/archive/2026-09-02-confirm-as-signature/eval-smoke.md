# Eval / smoke: подтверждение как подпись (фаза 2.6)

Прогон: `npx vitest run`, `bash delivery/evals/smoke/run.sh`, живая проба через протокол.
Галочка ставится по факту, а не по намерению; каждый оракул проверен обратным прогоном
(краснеет ли он без правки) — урок L7.

## Примеры спеки

- [ ] B14 — превью отдаёт `planId` из 6 символов; тот же код в HTML; значения «до» в плане
- [ ] B15 — `dryRun:false` без `confirm` → отказ `write.plan-confirmation`, ни одной записи
- [ ] B16 — `confirm` от другого плана → `plan_mismatch` + НОВЫЙ план и код в ответе
- [ ] B17 — таблицу правили между превью и записью → `stale_value` с названием ячейки
- [ ] B18 — `force` без `confirm` → отказ; с кодом плана, где отмечен `touches` → проходит
- [ ] B19 — записаны ровно ячейки плана: сверка журнала с планом
- [ ] B20 — повторный `confirm` на `appendRow` → `plan_already_applied`, второй строки нет
- [ ] B21 — `gc_undo` после записи с кодом → `undoOf` ссылается на `planId`

## Контурные оракулы

- [ ] `delivery_check` 0 ошибок
- [ ] smoke S1–S10 зелёные
- [ ] мутационный счёт не ниже 63.09% (замер фазы 2 — новый порог де-факто)
- [ ] обратный прогон: каждый новый оракул краснеет без своей правки

## Что этот сьют НЕ проверяет (названо, а не замолчано)

- **Смысловую правильность.** «Разрешённая цель, существующая колонка, значение из списка,
  ключ совпал — но проект не тот» механизмом не ловится. Средства против этого два, и оба
  уже есть: человек, читающий план, и `gc_undo`.
- **Прозу модели.** Код плана закрывает, ЧТО запишется, но не ЗАЧЕМ. Требовать от клиента
  показывать план дословно нельзя — это правило текстом, а не механизмом.
- **Подбор кода плана.** 6 hex — защита от случайного совпадения, не от вычислительно
  враждебного клиента.
